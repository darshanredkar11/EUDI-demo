What this demo is

A relying party asks a business question (“Is this user over 18?”). The system infers the minimum evidence that answers it, verifies a real cryptographic credential, and returns a deterministic ALLOW / DENY / UNKNOWN — revealing as little as possible.

Verifiable Credential (VC) — a signed, tamper-evident set of claims about a subject.

Verifiable Presentation (VP) — what the holder sends a verifier: the VC plus only the disclosures it chooses, plus proof it controls the credential (key binding).

SD-JWT VC — the IETF format used here: an issuer-signed JWT whose claims are hidden behind salted digests, each revealable via a separate “disclosure.”

Protocol mapping: this demo carries the same VC/VP artifacts OpenID4VP would — issuer-signed SD-JWT, selective disclosure, holder key binding, single-use nonce — over a simplified direct HTTP contract instead of the full OpenID4VCI (issuance) / OpenID4VP (presentation) envelopes. The artifacts are real; the transport layer is the next integration seam (see “Honest limitations”).

AI attack surface: the model has no tools, sees no PII, and its output is only accepted as one member of a closed, re-validated set — injection and hallucination collapse to a refusal.
